# Indus Weave HR Pipeline: Beginner Guide

This project takes HR source files (CSV and JSON), loads them into Microsoft SQL
Server, cleans and combines the data with Python, builds a reporting warehouse,
checks selected data-quality rules, and runs ten analysis queries.

## What happens to a CSV?

1. `ingestion/load_raw.py` uses `pandas.read_csv()` to read a CSV into a
   DataFrame (a table-like object in Python). JSON files are read with Python's
   built-in `json` module and converted to DataFrames too.
2. The loader calls `DataFrame.to_sql()` through SQLAlchemy. SQLAlchemy uses
   `pyodbc` and Microsoft's ODBC Driver to send the data to SQL Server. This
   creates/replaces a `dbo.raw__...` table; SSMS is for managing and querying
   the database, not for importing each file manually.
3. The transform scripts read those raw tables, clean or reshape them, then
   write `dbo.staging__...` tables.
4. Python builds daily attendance. SQL scripts create and fill warehouse
   tables. Analysis SQL can then be exported as CSV reports.

In the names above, `dbo` is SQL Server's default schema; `raw__` and `staging__`
are naming prefixes used by this project, not separate databases.

## Pipeline map

Run the complete pipeline from PowerShell in the project folder:

```powershell
python run_pipeline.py --reset --export
```

`--reset` drops only the pipeline tables before rebuilding them. It does not
delete the database or files, but it does delete the existing contents of those
tables. The `--export` option writes query results to `analytics/results/`.

| Order | File(s) | What it does |
|---|---|---|
| Setup | `setup_sql_server.sql` | Creates the `indus_weave` database if it does not exist. Run in SSMS once. |
| Settings | `config.py` | Holds source-file paths, SQL Server connection settings, and business-rule constants. |
| Runner | `run_pipeline.py` | Calls the stages in order, optionally resets project tables, and exports query results. |
| 1: Ingest | `ingestion/load_raw.py` | Reads the configured CSV/JSON files and replaces the matching raw tables. |
| 2: Employees | `transform/clean_employees.py` | Trims and standardizes employee fields, keeps the latest duplicate record, and records merged duplicates. |
| 2: History | `transform/clean_history.py` | Cleans employment history and derives each row's end date from the next effective date. |
| 2: Punches | `transform/clean_punches.py` | Maps device IDs to employees, corrects the documented device-clock issue, and separates invalid/duplicate punches. |
| 2: Leave | `transform/flatten_leave.py` | Flattens nested leave JSON, checks approvals/cancellation, and creates approved leave-day rows. |
| 2: Other tables | `run_pipeline.py` (`_clean_simple_tables`) | Copies simpler departments, shifts, roster, holiday, overtime, payroll, device, and application tables to staging. |
| 3: Attendance | `transform/build_attendance.py` | Creates an employee/day date spine and calculates attendance, hours, lateness, early departure, and overtime. |
| 4: Warehouse | `warehouse/ddl/01_dims.sql` | Recreates the date, department, shift, and employee dimensions. |
| 4: Warehouse | `warehouse/ddl/02_facts.sql` | Recreates attendance, leave, overtime, and payroll fact tables. |
| 4: Warehouse | `warehouse/ddl/03_load_warehouse.sql` | Loads the dimensions and facts from staging. |
| 6: Quality | `quality/run_checks.py` | Runs the checks listed in that file and appends their results to `dbo.dq_results`. |
| Reports | `analytics/q01_headcount.sql` – `q10_leave_overuse.sql` | Ten SQL Server analysis queries; `--export` saves their results as CSV files. |

`warehouse/erd.png` is a picture of the warehouse relationships. The
`__init__.py` files mark the Python folders as importable packages; they contain
no pipeline logic and should be kept. `run_pipeline.py` runs the whole process;
individual stage commands are listed in the README.

## Python dependencies

Only the packages in `requirements.txt` need installing:

| Package | Why it is used |
|---|---|
| `pandas` | Reads CSVs, transforms rows, and reads/writes SQL tables and report CSVs. |
| `numpy` | Supports array-based attendance status and calculations. |
| `SQLAlchemy` | Creates the SQL Server engine and provides the database interface used by pandas. |
| `pyodbc` | Lets SQLAlchemy communicate through Microsoft's SQL Server ODBC driver. |

`json`, `datetime`, `bisect`, `pathlib`, `os`, `urllib.parse`, `argparse`,
`time`, and `typing` are part of Python's standard library; they are not extra
packages. Microsoft ODBC Driver 18 is a separate Windows/SQL Server prerequisite,
not a Python package. There are no SQLite or MySQL dependencies in this setup.

## Source data and useful files

Keep the original files in `data/raw/`. The `data/raw/data_dictionary.md`
describes their columns and business rules. The CSV and JSON files there are
inputs: deleting one can make ingestion fail or remove data from the rebuilt
tables. The ten `analytics/q*.sql` files, the warehouse DDL, and the setup SQL
are also active project files.

The project is configured for Windows Authentication to the SQL Server instance
in `config.py`; it does not contain a database password. Set `SQL_SERVER`,
`SQL_DATABASE`, or `ODBC_DRIVER` environment variables if your machine uses
different values.

The attendance period is currently April 1 through September 30, 2026.
`config.py` controls the Python attendance date spine, but the warehouse date
load and some SQL checks/queries also contain this date range. Changing only
the Python setting will not change the entire report period.

One roster rule to be aware of: if an employee has no roster row for a week,
attendance now carries forward their most recent previous weekly shift. If
there is no earlier roster entry, it uses the general (`GEN`) shift.

## Safe cleanup guide

| Item | Recommendation |
|---|---|
| Original CSV/JSON files in `data/raw/` | Keep. They are required inputs. |
| `data/raw/data_dictionary.md` | Keep. It documents the input data and rules. |
| Analytics SQL and warehouse SQL | Keep. The pipeline and exports need them. |
| `analytics/results/*.csv` | Safe to delete if you do not need the old report copies; regenerate with `--export`. |
| `__pycache__/` and `*.pyc` | Generated Python cache; safe to remove, and Python recreates it. |
| Empty `logs/` folder | Not needed by the current print-based pipeline; safe to remove if it is empty. |
| `presentation/cfo_findings.md` | Not required to run the pipeline, but it was a human-readable report. It is already absent from the current working copy. |
| `transform/sql/attendance_daily.sql` | Obsolete SQLite-specific SQL; attendance is built by `transform/build_attendance.py`. It is already removed. |

There are no unnecessary third-party packages in the current
`requirements.txt`. Keep the dependency list short; do not install packages
just because they are commonly used in data projects.

## Checking the result in SSMS

After the pipeline finishes, connect to the configured SQL Server instance in
SSMS and select the `indus_weave` database. For example:

```sql
SELECT TOP (10) * FROM dbo.raw__employees;
SELECT TOP (10) * FROM dbo.staging__attendance_daily;
SELECT TOP (10) * FROM dbo.warehouse__fact_attendance_daily;
SELECT * FROM dbo.dq_results ORDER BY run_at DESC;
```

If a table is missing, verify that the required earlier stages completed.
Stage 4 needs the raw/staging data, and analytics exports need the warehouse
tables.

## Current validation limits

The quality-check code runs a selected set of checks, not every possible key,
foreign key, reconciliation, or accepted-value check. Its `CHECKS` list is the
authoritative list of checks currently implemented. A printed quality-check
failure is recorded in `dq_results`; it does not automatically stop the later
pipeline stages.

T.
Python dependencies and the SQL Server connection must be available on the
machine that runs it.
